# Pipeline

## Задача
Собрать несколько стадий обработки данных в цепочку так, чтобы каждая стадия
работала в своей горутине и общалась с соседними через каналы — и корректно
останавливалась, если потребитель прекращает читать раньше, чем данные
кончились.

## Решение
См. [pipeline.go](pipeline.go). `Generate(ctx, n)` — источник, шлёт `n`
случайных значений с интервалом 100мс. `Multiply(ctx, in, x)` — стадия
преобразования, читает из `in` и шлёт `x*v` в свой выходной канал. Стадии
собираются в цепочку вызовом `Multiply(ctx, Generate(ctx, n), x)`.

## Подводные камни
- Если потребитель прекращает читать выходной канал раньше, чем стадии
  исчерпают данные, горутины навсегда зависают на блокирующей отправке —
  классическая утечка pipeline-паттерна. Нужен общий сигнал остановки; здесь
  эту роль играет `ctx`, который обязательно нужно передавать в обе стадии
  и отменять на стороне вызывающего кода при раннем выходе.
- Закрывать выходной канал стадии может только сама эта стадия
  (`defer close(out)`) — потребитель никогда не должен закрывать чужой
  канал.
- Каждый `select` на отправку в `out` обязан также слушать `ctx.Done()` —
  иначе стадия не заметит отмену, пока где-то дальше по цепочке не
  появится читатель.
- `Multiply` слушает `ctx.Done()` не только на отправке, но и на приёме из
  `in` — иначе она может надолго зависнуть на `<-in`, если стадия выше по
  цепочке уже остановилась и не пришлёт значение (хотя корректно
  работающий upstream в этом случае закроет `in`, и приёма без данных не
  произойдёт).

## Бенчмарки
Бенчей нет — стадии искусственно замедлены `time.Sleep`/`time.After` для
наглядности, поэтому throughput-бенчмарк здесь не показателен; корректность
и отсутствие утечек горутин проверяются обычными тестами.
