# Rate Limiter (Token Bucket)

## Задача
Ограничить частоту вызовов: не больше `limit` разрешений за `period`, но с
возможностью мгновенного всплеска (burst) до `limit` подряд, если токены
успели накопиться — в отличие от простого "не больше N в фиксированном окне",
это сглаживает скорость, а не просто режет её по границе окна.

## Решение
См. [limiter.go](limiter.go). Токены хранятся в буферизованном канале
ёмкостью `limit`, изначально заполненном полностью — это и даёт разрешённый
burst сразу после создания. Фоновая горутина по тикеру с интервалом
`period/limit` добавляет один токен (не блокируясь, если ведро уже полно).
`Allow()` — неблокирующая попытка забрать токен.

## Подводные камни
- Это не «книжный» token bucket с независимыми параметрами: `capacity`
  (burst) и скорость пополнения здесь жёстко связаны одним `limit` — нельзя
  задать «burst 1000, но стабильно 10/сек» отдельно друг от друга.
- `limit <= 0` или `period <= 0` — паника уже в конструкторе, а не
  `integer divide by zero` где-то в рантайме.
- Фоновая горутина пополнения живёт, пока не отменён `ctx`, переданный в
  конструктор. Долгоживущий лимитер должен получить `ctx`, который
  вызывающий код реально отменяет при остановке — иначе горутина течёт до
  конца жизни процесса.
- Целочисленное деление `period/limit` усекает интервал пополнения — при
  больших `limit` реальная скорость может слегка отличаться от заявленной
  (дрейф на длинной дистанции).
- `Allow()` — только неблокирующий вызов. Блокирующего `Wait(ctx)`, который
  бы ждал появления токена с уважением к отмене контекста, здесь нет.
