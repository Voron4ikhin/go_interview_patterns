# Sharded map

## Задача
Реализуйте потокобезопасную map, которая масштабируется на конкурентную нагрузку лучше, чем один `map` под одним `sync.Mutex`/`sync.RWMutex`: данные делятся на независимые шарды, каждый со своей блокировкой, чтобы операции над разными ключами не конкурировали за один и тот же мьютекс.

## API

- `NewShardedMap[K comparable, V any](shardCount int, hash HashFunc[K]) *ShardedMap[K, V]` — паникует, если `shardCount <= 0` или `hash == nil`.
- `NewStringShardedMap[V any](shardCount int) *ShardedMap[string, V]` — `NewShardedMap` с готовой хеш-функцией `FNV32String` для строковых ключей.
- `FNV32String(key string) uint32` — хеш FNV-1a, дефолтная хеш-функция для строк.
- `Get(key K) (V, bool)` / `Set(key K, value V)` — базовые операции.
- `Delete(key K) bool` — удаляет ключ, возвращает, существовал ли он.
- `Contains(key K) bool` — проверяет наличие ключа.
- `Len() int` — суммарное количество элементов по всем шардам.
- `Keys() []K` — все ключи по всем шардам.
- `Clear()` — очищает все шарды.
- `Range(fn func(key K, value V) bool)` — проходит по всем элементам шард за шардом, останавливается, если `fn` вернёт `false`.

## Реализация

- `ShardedMap[K, V]` — это `[]*shard[K, V]`, каждый шард — обычная `map[K]V` под своим `sync.RWMutex`. Шард для ключа выбирается как `hash(key) % len(shards)`; хеш-функция передаётся снаружи и должна быть детерминированной, чтобы один и тот же ключ всегда попадал в один и тот же шард.
- Хеш-функция вынесена наружу через `HashFunc[K]`, а не зашита в тип: сравнение ключей и их хеширование — ответственность вызывающего кода, а не структуры данных. Для строк есть готовый `FNV32String` (FNV-1a) — быстрый, без лишних аллокаций, с хорошим распределением по бакетам.
- `Get`/`Set`/`Delete`/`Contains` трогают только свой шард и блокируют только его — это и есть весь смысл шардирования: конкурентные операции над ключами из разных шардов не блокируют друг друга.
- `Len`, `Keys`, `Range`, `Clear` проходят по шардам последовательно, блокируя каждый шард только на время своей части работы, а не все шарды сразу. Из-за этого они не дают atomic-снепшот всей map под конкурентной записью (запись в уже пройденный шард между визитами возможна) — это осознанный компромисс в пользу меньшей блокировки, а не баг.
- Число шардов фиксировано на конструкторе: ре-шардирование (rehash при росте нагрузки) не реализовано, как и в большинстве учебных вариантов этого паттерна.
